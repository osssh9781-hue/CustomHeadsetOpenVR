# 컷 엔진 최적화 검토 — 국소 Boolean vs 국소 SDF (2026-10-29, 0.24.86 기준)

측정은 전부 이 저장소의 스크립트로 돌린 것입니다(`tools_dev/bench/bench_region.py`, `bench_cut.py`, `bench_sdf.py`; 로그 `tests/bench_region_0.24.86.txt`, `tests/bench_sdf_ico9_0.24.86.txt`, `tests/bench_region_fast_proto.txt`). 4코어 리눅스 컨테이너 · Blender 5.2.3 bpy · 창 없음. **"예상"이라고 적은 숫자는 측정이 아닙니다.** 9950X3D 에서는 더 빠르겠지만 비율은 비슷할 것으로 봅니다(미측정).

## 0. 왜 Substance 3D Modeler 는 1억 "폴리곤"에서도 부드러운가

Modeler 의 장면은 폴리곤이 아니라 **희소 복셀 SDF(부호 거리장)** 입니다. "1억 폴리곤 상당"은 복셀 해상도를 폴리곤으로 환산한 수치입니다. 그 구조에서 컷은:

- **손댄 브릭(8³ ~ 16³ 복셀 묶음)만 다시 계산**합니다. 거리장 뺄셈은 복셀마다 `max(a, -b)` 한 줄이라 GPU 에서 수만 개 브릭도 1 ms 대입니다.
- **메시를 만들지 않습니다.** 화면은 거리장을 직접 레이마칭으로 그립니다. 그래서 8K VR 렌더와 컷이 같이 돌아도 "메시 재구성 → GPU 업로드" 단계가 없습니다.
- 토폴로지가 없으니 자기 교차 · 열린 변 · 슬리버 같은 문제 자체가 없습니다. 대신 **평면과 날카로운 엣지는 복셀 해상도만큼만 정확**합니다(아래 측정).

블렌더 + 메카닉랩의 컷은 반대편 끝입니다: 명시적 폴리곤 메시에서 **정확한 교차선을 계산하고(Exact/Manifold 불리언), 메시 전체를 새 datablock 으로 다시 쓰고, 뷰포트가 130만 면을 GPU 로 다시 올립니다.** 거기에 애드온은 파이썬이라 "메시 전체를 한 번 읽고 쓰는" 비용(0.24.86 에서 100배 줄였지만 아직 0.1 ~ 0.3초)이 단계마다 붙습니다. "버벅임"의 정체는 불리언이 아니라 **메시 전체를 다시 만드는 횟수와 그 크기**입니다. 아래 측정이 그 증거입니다.

뷰포트가 바뀐 130만 면을 GPU 로 다시 올리는 시간은 창 없는 환경이라 **측정 못 했습니다**(0.2 ~ 0.5초로 예상, 어떤 엔진을 쓰든 메시 datablock 이 바뀌면 피할 수 없음).

## 2. 국소 Boolean vs 국소 SDF — 측정으로 비교

### 2-1. 국소 SDF 의 비용과 품질 (측정)

컷 영역(1.3M 부품의 커터 상자 안, 16,299면, 닫힌 껍질)을 Exact 로 정확히 자른 뒤(15,726면), 그 결과를 **블렌더 자체 OpenVDB 복셀 리메시**(새 의존성 없이 쓸 수 있는 가장 빠른 SDF)로 다시 샘플링했습니다. 커터는 복셀 격자와 안 맞게 15° · 10° · 20° 돌려 둠. 평균 변 길이 0.00489 (부품 크기 2.4).

| | 시간 | 면 수 | 벽 점의 평면 오차 rms / 최대 | 벽 면적 중 노멀이 평면 1° 안 | 벽 모서리의 둥글어진 면적 비율 |
|---|---|---|---|---|---|
| **Exact 불리언(기준)** | 0.26 ~ 1.8 | 15,726 | **1e-8 / 2e-8** | **100 %** | **0 %** |
| SDF 복셀 = 변 길이 | 0.65 | 143,382 (×9) | 6.3e-4 / 7.3e-3 (변 길이의 13 % / 150 %) | 95.7 % | 11.4 % |
| SDF 복셀 = 변 길이 / 2 | 2.12 | 569,890 (×36) | 2.2e-4 / 3.7e-3 | 97.9 % | 5.9 % |
| SDF 복셀 = 변 길이 / 4 | 8.21 | 2,283,992 (×145) | 7.9e-5 / 1.8e-3 | 99.0 % | 3.1 % |
| (참고) 부품 전체를 변 길이로 SDF 화 | 3.33 | 852,410 (1.3M → 85만, 디테일 손실) | | | |

읽는 법:
- **정확한 평면은 복셀 해상도만큼만 평면**입니다. 변 길이와 같은 복셀이면 벽 점이 평면에서 최대 변 길이 1.5배까지 벗어나고, 벽 모서리(벽과 표면이 만나는 날카로운 엣지) 띠의 11 %가 둥글어집니다. 메카닉랩의 Hard Edges · Quad Remesh · Client Look 은 **"평면인 벽 + 날카로운 엣지"** 를 찾아 동작하므로 이것은 품질 요구("하드서피스의 정확한 평면과 날카로운 엣지")와 직접 충돌합니다.
- 오차를 줄이려면 복셀을 4분의 1로 — 그러면 영역 하나가 **228만 면**이 되고 8초가 걸립니다. 국소여도 느려지고, 결과 메시가 원본보다 훨씬 무거워집니다.
- 이 측정은 "이미 정확히 자른 결과를 SDF 로 옮기기만 한" **SDF 의 최선**입니다. 진짜 SDF 엔진은 부품 표면도 복셀화하므로 영역 전체(컷과 무관한 표면 포함)가 리샘플링되어 디테일 · UV · 마스크 · 폴리그룹 · 색이 **사라지거나 재투영**되어야 합니다.
- Modeler 가 이 문제를 안 느끼는 이유: 화면이 거리장 자체라 "면"이 없고, 하드서피스 엣지도 복셀 해상도를 아주 높여(GPU 메모리로) 감춥니다. 블렌더에서는 결국 메시를 꺼내야 하므로 그 비용이 그대로 드러납니다.

### 2-3. 판단

**국소 Boolean 을 계속 갑니다.** 이유는 속도가 아니라 품질 조건입니다: 정확한 평면과 날카로운 엣지는 SDF 로는 해상도를 올려 흉내 내는 것이고, 올릴수록 면 수와 시간이 폭발합니다(측정). 그리고 SDF 를 써도 "영역 결과를 원본 메시에 꿰매고 메시 전체를 다시 쓰는" 비용 — 지금의 진짜 병목 — 은 그대로 남습니다.

국소 SDF 가 맞는 자리는 하나입니다: **크리처 표면에 조각 느낌으로 파는 컷**(DynaMesh 를 어차피 다시 돌릴 부품). 그건 지금도 "컷 → DynaMesh" 로 같은 결과를 얻으므로 새 엔진이 필요하지 않습니다.

## 3. 그럼 "즉각 반응"은 어떻게 — 다음 단계 제안

병목이 "메시 전체 다시 쓰기"이므로 방향은 두 가지뿐입니다: **더 적게 쓰거나, 나중에 쓰거나.**

### A. 국소 Boolean v2 (프로토타입 있음, 측정 2.31초 @1.3M)
1. 결과 얹기를 datablock 교체로(완료, 프로토타입). 
2. 꿰매기에서 정리한 결과는 뒤에서 다시 검사하지 않음(완료, 프로토타입).
3. 꿰매기 안의 "128만 면 복사" 줄이기 — 있는 속성만 옮기기(사용자 메시는 보통 마스크 · 페이스셋 정도), 변 속성은 sharp_edge 가 있을 때만, 변 키를 numpy 정렬 대신 해시로. **예상** 1.2 → 0.6초.
4. 꿰매기를 C 로(ctypes, mdecim 처럼 Linux/Windows 빌드) — 기하 + 속성 복사를 memcpy 로. **예상** 0.6 → 0.3초. 
5. 같은 부품에 연달아 컷할 때 메시 배열을 캐시(읽기 생략). **예상** 0.1초.
→ 1.3M 라쏘 컷 **약 1.2 ~ 1.5초 예상**(불리언 0.4 + 꿰매기 0.3 ~ 0.6 + 기타 0.3 + 뷰포트 업로드). 여기가 "메시 전체를 다시 쓰는 구조"의 바닥입니다.

### B. 미룬 꿰매기(deferred stitch) — Modeler 느낌에 가장 가까운 길
컷 결과 중 **영역만 즉시 보여주고**(2만 면짜리 임시 오브젝트, 원본은 그 자리 면만 숨김), **메시 전체 다시 쓰기는 타이머/백그라운드에서** 합니다. 사용자는 0.5초 안에 잘린 모습을 보고 다음 획을 긋고, 같은 영역에 겹치는 획은 영역 메시에 누적된 뒤 한 번만 꿰맵니다. 0.24.86 의 백그라운드 작업 틀(bg_jobs)을 그대로 씁니다.
- 즉시 보이는 부분: 영역 찾기 0.2 + 불리언 0.4 + 임시 표시 0.1 = **0.7초 예상**(1.3M), 부품 크기와 거의 무관.
- 문제점: 꿰매기 전 상태에서 Ctrl+Z · 선택 · 내보내기 · 다른 도구가 그 부품을 만지면 어떻게 할지(꿰매기를 먼저 강제), 두 메시가 겹쳐 보이는 동안의 음영 이음새, 임시 오브젝트의 정리. 구현 2 ~ 3일.

### C. 하지 않을 것
- 블렌더 소스 수정(불리언 멀티스레딩): 불리언은 전체의 15 %라 효과 없음(측정).
- GPU: 이 컨테이너엔 GPU 가 없어 측정 자체가 불가능하고, 위 구조에서 GPU 가 필요한 단계가 없음.

## 4. 검증 방법(이미 있는 것 + 추가)

- **동일성**: `bench_region.py` — 세 부품 × 두 커터 × Cut/Split 에서 부피 차 1e-6 이하 · 열린 변 0 · 컷 바깥 면 비트 동일 · 속성 · 재질 (0.24.86 통과).
- **안정성**: 영역 경로 강제 컷 기하 93/93, 파이프라인 퍼즈 20 × 12 두 번, GUI 13/13 (0.24.86 통과). v2 · B 도 같은 묶음 + 전체 테스트.
- **속도**: `bench_cut.py` 단계별 시간(같은 실행에서 끄고/켜고). 이 문서의 모든 숫자가 이것.
- **품질(하드서피스)**: `bench_sdf.py` 의 벽 평면 오차 · 엣지 둥글어짐 측정을 v2 결과에도 적용(목표: 기준과 같은 1e-8 / 0 %).
- **B 추가**: 미룬 꿰매기 중 Ctrl+Z · 선택 · 내보내기 · 재컷 시나리오를 퍼즈에 넣기; 창 테스트에서 임시 오브젝트가 남지 않는지.

## 5. 추천
